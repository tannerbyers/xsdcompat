# Recommended GitHub Repository Settings

Some project security and review controls live in GitHub settings rather than version-controlled files. This document records the intended configuration so those controls remain reviewable and reproducible.

The exact GitHub UI/API names may change over time; preserve the security property rather than blindly following stale menu wording.

## Default branch

Use `main` as the default branch.

## Branch/ruleset protection for `main`

Recommended baseline once the initial documentation PR is merged:

- prohibit force pushes;
- prohibit branch deletion;
- require changes to enter through pull requests for normal development;
- require all review conversations to be resolved before merge;
- require configured CI checks after CI exists;
- require the branch to be up to date when doing so materially protects the test result, balancing this against unnecessary contributor friction;
- apply rules to administrators where practical, with an emergency/break-glass path documented rather than routine bypass.

For a single-maintainer project, requiring an independent approving reviewer can make normal maintenance impossible. Add mandatory approval counts when there is a second active maintainer rather than creating a rule that must constantly be bypassed.

## Merge strategy

Prefer squash merge for ordinary PRs so focused PRs produce one coherent main-branch commit even when the working branch contains iterative commits.

Rebase merge can remain available when preserving logically separate clean commits is useful.

Consider disabling merge commits if the project wants a consistently linear history; this is a history/readability choice, not a security requirement.

## CODEOWNERS

`.github/CODEOWNERS` currently assigns the repository owner. When maintainership expands, replace the blanket ownership model with appropriate maintainer/team ownership and enable code-owner review for sensitive paths when there are enough maintainers to satisfy it without bypasses.

Sensitive future paths may include:

```text
.github/workflows/
internal/source/
internal/xmlscan/
internal/schema/
internal/compat/
docs/adr/
SECURITY.md
```

## Private vulnerability reporting

Enable GitHub private vulnerability reporting / Security Advisories if available for the repository.

`SECURITY.md` directs reporters to that channel and provides a fallback that does not require publishing exploit details.

## Security features

Enable available GitHub security features where they fit the repository/account plan, including:

- secret scanning / push protection;
- dependency graph;
- Dependabot/security alerts for GitHub Actions or future dependencies;
- code scanning when implementation begins and the signal is useful.

The zero-third-party-Go-module policy does not remove the need to monitor GitHub Actions and the Go toolchain/runtime.

## GitHub Actions

When workflows are introduced:

- set default `GITHUB_TOKEN` permissions to read-only;
- grant write/attestation/release permissions only to jobs that require them;
- keep release permissions away from pull-request jobs;
- pin third-party actions by immutable full commit SHA;
- use OIDC/short-lived credentials instead of stored cloud credentials where possible;
- review actions before adoption and keep the action set intentionally small;
- avoid `pull_request_target` for workflows that execute untrusted PR code unless the security implications are explicitly understood and reviewed.

## Release controls

Official releases should be generated by the repository release workflow described in `docs/RELEASE.md`.

Recommended properties:

- tags/releases are created by maintainers or controlled automation;
- official binaries are never manually replaced after publication;
- release artifacts include checksums, SBOM, and provenance/attestation by 1.0;
- release environments may require maintainer approval if that provides useful separation of duties.

## Discussions

GitHub Discussions is optional. Enable it when there is enough user activity to separate questions/design discussions from actionable bug reports. Until then, keeping the number of support surfaces small reduces maintenance burden.

## Wikis / Projects

Do not use a separate GitHub Wiki for normative architecture/security documentation; keep authoritative project docs version-controlled in the repository.

GitHub Projects may be introduced for planning if it becomes useful, but roadmap/project-board state must not become the only record of architectural decisions.

## Repository visibility and archival

The project is intentionally public/open source.

If maintenance ends, archive the repository or clearly mark it unmaintained rather than leaving users to infer support status from inactivity.

## Periodic review

Review repository settings:

- before 1.0;
- whenever maintainers are added/removed;
- when release automation changes;
- after a security incident;
- when GitHub introduces materially better security controls.
